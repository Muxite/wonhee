What we did

Each node runs in its own container. The host reads that container's CPU and memory counters, and Nsight records every GPU kernel the node's own process launches, so a node's data stays its own even when others share the GPU. Per-node traces you can reuse

Any profiled run exports as one JSON file per node (parameters, hardware, who else shared the GPU, its slowdown against solo, and every GPU kernel and memory copy with timing and launch shape), plus a Perfetto-viewable trace. Identical runs launch identical kernel sequences, so a node's solo and shared traces line up kernel for kernel, which is useful for checking a simulator's contention model.

Kernels, copies, VRAM, CPU and RAM belong to the node alone. GPU-wide counters (utilization, power, DRAM, tensor) belong to the node only when it ran alone, and each run records whether it did.

Would this hold on a unified-memory ARM system?

Everything here was measured on x86-64 with a discrete GPU: its own 16 GB of memory, joined to the CPU's RAM over PCIe. Unified-memory aarch64 systems (NVIDIA Grace-based machines, Jetson, Apple silicon) give the CPU and GPU one shared memory pool. These are expectations, not measurements.

Likely to carry over

  • Decode is memory-bandwidth-bound. It re-reads all weights per token on any hardware; speed scales with that system's memory bandwidth, which on unified LPDDR designs is often lower than this card's.
  • Batching beats separate processes. One weight read serving many streams is a property of the workload, not the platform.
  • Separate processes take turns on the GPU and lose time switching, wherever the driver time-slices contexts. The size of the switching tax needs remeasuring.
  • Container start is a fixed cost per launch. Docker and runc work the same way; the absolute milliseconds depend on the CPU.

Needs remeasuring

  • Model loading and cold start. No PCIe copy into separate GPU memory, so the gap between "in RAM" and "in GPU memory" (2.7 s vs 0.05 s here) may shrink or vanish.
  • Partial offload. The cliff here comes from layers running on the CPU across PCIe. With one pool, the trade-off between CPU and GPU execution looks different.
  • CPU jobs competing with GPU jobs. Here CPU work (subtitle encoding, speech startup) barely touched the GPU. On shared memory, CPU and GPU draw on the same bandwidth, so new interference is likely.
  • Memory accounting. "GPU memory" and RAM are the same pool: per-process attribution, OOM limits and cgroup numbers can overlap and need re-validating.
  • Counters and power. Which hardware counters and per-process readings are available differs by chip, and power is often reported for the whole chip, not the GPU alone.
  • Software. Every image needs an arm64 build, and hardware video encoders differ by platform.

Open questions

  • Does a smarter GPU sharing mode change the picture? NVIDIA MPS or MIG could let separate processes overlap instead of taking turns. Not tested; MIG is not available on this consumer card.
  • Where does batching stop paying off? The jump at 8 streams comes from llama.cpp switching to batched matrix kernels. Larger batches, longer contexts and larger models would locate the limit.
  • How general are these numbers? One machine and one GPU. Rerunning the same gauge experiments on a datacenter GPU and on a unified-memory ARM system would test which shapes carry over (see above).
  • What is the switching tax made of? Two identical LLMs lose about 22% of the GPU's work when interleaved. Context-switch time, cache and TLB refills, or launch queuing are all candidates; MPS, which removes context switches, would separate them.
  • Can a simple model predict Fig. 5? The time-split model in Fig. 8 plus a switching tax is a start. Each node's kernel lengths and position in Fig. 6 might be enough to predict its share of GPU time; the exported traces are the test set.
  • Real agent traffic. These are steady runs. Bursty agent calls with gaps, model swaps and cold starts behave differently and are not measured here.
